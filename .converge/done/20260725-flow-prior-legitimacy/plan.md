# Plan：流程先验合法性判据的三仓库贯彻

## 背景

2026-07-25 对话共识（用户确认）：Bitter Lesson 反对的是**封顶型先验**（任务知识、局部最优启发式——随模型变强减值），不反对**防呆型机制**（契约校验、过程监督、预算门控——防御机械失误；机械失误随任务量缩放、不随模型强度缩放，故此类机制随模型变强不过时）。流程先验（脚本化调度）合法性的三分判据：

1. 机制不执行任务本身；
2. 不收窄模型可达的解空间——流程先验必须留逃生舱，且逃生舱真实可用；
3. 对契约违反 fail-closed（拦机械错误），对判断分歧 fail-open（不否决自己不理解的判断）。

## 改动范围（三处，同一原则的层间映射，不互相复制全文）

| 仓库 | 文件 | 落点 |
|------|------|------|
| init-agent-docs | `SKILL.md` 哲学第 8 条 | 原则的**权威表述**（封顶型 vs 防呆型 + 三分判据） |
| converge | `CONSTITUTION.md` 第一部 | 哲学锚点 + 把既有 `需重新设计` / `contract_amendment_required` 命名为逃生舱的兑现 |

## 验收标准

1. 三处改动语义一致（同一判据三层表述），无全文复制
2. converge 宪法修改经 ultraverge（≥3 Reviewer，三族并行）+ 设计审查 + 用户人工确认
3. 各仓库既有测试/校验通过（init-agent-docs: pytest；ocsr/converge: 无测试则人工核对引用完整性）
4. 每个仓库单独提交，提交前用户确认

## 流程

起草（本计划 + 三处编辑）→ ultraverge 打包评审（3 族并行，OCSR 派发）→ 修复 → 盲审 → 设计审查 → 用户确认 → 分别提交
